Informe de Mejoras: Problemas Opcionales 1 y 3

El presente documento describe las dos mejoras implementadas sobre el prototipo de red social, correspondientes a los Problemas Opcionales 1 y 3. Para cada mejora se detalla el problema que se resuelve, la estrategia algorítmica elegida, el análisis de complejidad, la explicación de la implementación y los fragmentos de código relevantes.

Algoritmos aplicados:

  • Problema Opcional 1: BFS (Breadth-First Search) — detección de componentes conexas tras un bloqueo.
  • Problema Opcional 3: Programación Dinámica con máscara de bits (bitmask DP) — asignación óptima de administradores.

Problema Opcional 1: Simulación de Bloqueos y Conexiones Alternativas

1.1. Problema que se intenta resolver

En una red social, cuando un usuario bloquea a otro se elimina la conexión directa entre ambos. Esto puede tener un efecto colateral grave: si esa conexión era un puente (la única vía que unía dos regiones del grafo), la red queda desconectada en dos o más componentes aisladas, impidiendo que ciertos usuarios se comuniquen entre sí.

El problema se descompone en tres subproblemas:

  1. Detección: Dado un bloqueo entre los usuarios A y B, ¿el grafo resultante sigue siendo conexo?
  2. Diagnóstico: Si no es conexo, ¿cuántas componentes conexas se forman y qué usuarios pertenecen a cada una?
  3. Restauración: ¿Cuál es el número mínimo de conexiones nuevas necesarias para reconectar el grafo, y entre qué usuarios deberían crearse?

1.2. Estrategia elegida: BFS (Breadth-First Search)

Se eligió BFS (Búsqueda en Anchura) como algoritmo principal por las siguientes razones:

  • Es el algoritmo estándar para encontrar componentes conexas en un grafo no ponderado, que es exactamente lo que se necesita después de eliminar una arista.
  • Tiene complejidad óptima O(V + E), ya que visita cada nodo y arista exactamente una vez.
  • Su implementación iterativa con cola evita problemas de desbordamiento de pila (a diferencia de DFS recursivo) para grafos grandes.
  • El recorrido por niveles permite descubrir la componente conexa completa de un nodo de forma sistemática.

Descripción de la estrategia paso a paso:

  1. Construcción de la adyacencia modificada: Se genera una lista de adyacencia no dirigida a partir del grafo original, excluyendo la conexión bloqueada en ambas direcciones. El grafo original es dirigido, pero para evaluar la conectividad en una red social (donde la amistad es bidireccional) se trata como no dirigido.
  2. BFS iterativo para componentes: Se recorren todos los nodos. Para cada nodo aún no visitado, se inicia un BFS que descubre toda su componente conexa. El BFS utiliza una cola FIFO: encola el nodo origen, y mientras la cola no esté vacía, desencola un nodo, y para cada vecino no visitado lo marca y lo encola.
  3. Evaluación de conectividad: Si se encontró más de una componente, el grafo está desconectado.
  4. Cálculo de restauración: Para C componentes se necesitan exactamente C − 1 conexiones nuevas. Se conectan componentes adyacentes buscando, cuando sea posible, aristas de bajo peso del grafo original.

1.3. Complejidad del algoritmo y del programa

Aspecto Complejidad Justificación
Construcción de adyacencia O(V + E) Se recorren todos los usuarios (V) para inicializar y todas las conexiones (E) para poblar la lista de adyacencia.
BFS (detección de componentes) O(V + E) Cada nodo se encola y desencola exactamente una vez; cada arista se examina dos veces (una por cada extremo en el grafo no dirigido).
Cálculo de restauración O(C · E) Para cada par de componentes adyacentes (C − 1 pares), se recorren las conexiones originales buscando la de menor peso. En la práctica C es pequeño.
Total temporal O(V + E) Dominado por la fase de BFS; la restauración es O(C · E) pero C ≤ V y típicamente C « V.
Total espacial O(V + E) Lista de adyacencia no dirigida + conjunto de visitados + cola BFS.

1.4. Explicación de la implementación

La mejora se implementó en la clase ConectividadBFS dentro del paquete org.uade.progra3.grafos. La clase es puramente estática (todos sus métodos son static) y contiene una clase interna ResultadoBloqueo que encapsula el resultado de la simulación.

Flujo de ejecución:

  1. El método público simularBloqueo(grafo, bloqueador, bloqueado) actúa como punto de entrada.
  2. Llama a construirAdyacenciaNoDir() que recorre todas las conexiones del grafo y construye un Map<Usuario, List<Usuario>> excluyendo la conexión bloqueada.
  3. Llama a encontrarComponentesBFS() que itera sobre todos los usuarios y, para cada usuario no visitado, lanza un bfs() que explora su componente conexa completa usando una Queue<Usuario> (cola FIFO).
  4. Si hay más de una componente, llama a calcularRestauracion() que sugiere C − 1 conexiones entre componentes consecutivas.
  5. Retorna un ResultadoBloqueo con: si el grafo es conexo, la lista de componentes, y las conexiones de restauración sugeridas.

Integración con el resto del sistema:

  • RedSocialServicio expone el método simularBloqueo() que delega en ConectividadBFS.
  • RedSocialFrame agrega una nueva pestaña “Bloqueo (BFS)” con dos combo boxes para seleccionar usuarios y un área de texto para mostrar resultados.
  • No se modificó la estructura del grafo original: la simulación trabaja sobre una copia de la adyacencia.

public static ResultadoBloqueo simularBloqueo(Grafo grafo,
                                              Usuario bloqueador,
                                              Usuario bloqueado) {
    // 1. Construir adyacencia no dirigida sin la arista bloqueada
    Map<Usuario, List<Usuario>> adyacencia =
            construirAdyacenciaNoDir(grafo, bloqueador, bloqueado);

    // 2. Encontrar componentes conexas mediante BFS
    List<List<Usuario>> componentes =
            encontrarComponentesBFS(adyacencia, grafo.getUsuarios());

    // 3. Evaluar conectividad y calcular restauración si es necesario
    boolean conexo = componentes.size() <= 1;
    List<Conexion> restauracion = new ArrayList<>();

    if (!conexo) {
        restauracion = calcularRestauracion(componentes, grafo,
                                            bloqueador, bloqueado);
    }

    return new ResultadoBloqueo(conexo, componentes, restauracion);
}

Construcción de adyacencia excluyendo la arista bloqueada
Archivo: src/main/java/org/uade/progra3/grafos/ConectividadBFS.java

private static Map<Usuario, List<Usuario>> construirAdyacenciaNoDir(
        Grafo grafo, Usuario bloqueador, Usuario bloqueado) {
    Map<Usuario, List<Usuario>> adj = new HashMap<>();
    for (Usuario u : grafo.getUsuarios()) {
        adj.put(u, new ArrayList<>());
    }

    for (Conexion c : grafo.getConexiones()) {
        boolean esBloqueada =
            (c.getOrigen().equals(bloqueador) &&
             c.getDestino().equals(bloqueado)) ||
            (c.getOrigen().equals(bloqueado) &&
             c.getDestino().equals(bloqueador));
        if (esBloqueada) continue;

        adj.get(c.getOrigen()).add(c.getDestino());
        adj.get(c.getDestino()).add(c.getOrigen());
    }
    return adj;
}

BFS iterativo para descubrir una componente conexa
Archivo: src/main/java/org/uade/progra3/grafos/ConectividadBFS.java

private static List<Usuario> bfs(Usuario origen,
                                  Map<Usuario, List<Usuario>> adj,
                                  Set<Usuario> visitados) {
    List<Usuario> componente = new ArrayList<>();
    Queue<Usuario> cola = new LinkedList<>();
    cola.add(origen);
    visitados.add(origen);

    while (!cola.isEmpty()) {
        Usuario actual = cola.poll();
        componente.add(actual);

        for (Usuario vecino : adj.getOrDefault(actual,
                                     Collections.emptyList())) {
            if (!visitados.contains(vecino)) {
                visitados.add(vecino);
                cola.add(vecino);
            }
        }
    }
    return componente;
}

Archivo: src/main/java/org/uade/progra3/grafos/ConectividadBFS.java

private static List<Conexion> calcularRestauracion(
        List<List<Usuario>> componentes, Grafo grafo,
        Usuario bloqueador, Usuario bloqueado) {
    List<Conexion> nuevas = new ArrayList<>();

    Map<Usuario, Integer> componenteDeUsuario = new HashMap<>();
    for (int i = 0; i < componentes.size(); i++) {
        for (Usuario u : componentes.get(i)) {
            componenteDeUsuario.put(u, i);
        }
    }

    // Conectar componente i con componente i+1 (C-1 conexiones)
    for (int i = 0; i < componentes.size() - 1; i++) {
        Conexion mejor = null;
        for (Conexion c : grafo.getConexiones()) {
            // Excluir la conexión bloqueada
            boolean esBloqueada = /* ... verificación ... */;
            if (esBloqueada) continue;

            int compOrigen = componenteDeUsuario.get(c.getOrigen());
            int compDestino = componenteDeUsuario.get(c.getDestino());
            if ((compOrigen == i && compDestino == i + 1) ||
                (compOrigen == i + 1 && compDestino == i)) {
                if (mejor == null || c.getPeso() < mejor.getPeso()) {
                    mejor = c;
                }
            }
        }
        if (mejor != null) {
            nuevas.add(mejor);
        } else {
            nuevas.add(new Conexion(componentes.get(i).get(0),
                                    componentes.get(i + 1).get(0), 1));
        }
    }
    return nuevas;
}

Problema Opcional 3: Asignación Óptima de Administradores a Grupos

2.1. Problema que se intenta resolver

La red social cuenta con n grupos temáticos y m administradores disponibles (con m ≥ n). Cada administrador tiene un valor de ineficiencia distinto para cada grupo, representado en una matriz de costos costos[i][j] donde i es el grupo y j es el administrador. El objetivo es encontrar una asignación uno a uno (cada grupo recibe exactamente un administrador, cada administrador administra como máximo un grupo) que minimice la suma total de ineficiencias.

Este es una instancia del clásico Problema de Asignación (Assignment Problem), que es NP-hard en su forma general de fuerza bruta (O(n!) permutaciones), pero puede resolverse eficientemente mediante programación dinámica.

Ejemplo concreto (datos del prototipo):

Admin-Ana Admin-Pedro Admin-Maria Admin-Jorge
Programación 9 2 7 8
Arte Digital 6 4 3 7
Ciencias 5 8 1 8
Deportes 6 6 9 4

La asignación óptima resulta: Programación → Admin-Pedro (costo 2), Arte Digital → Admin-Ana (costo 6), Ciencias → Admin-Maria (costo 1), Deportes → Admin-Jorge (costo 4). Costo total mínimo: 13.

2.2. Estrategia elegida: Programación Dinámica con máscara de bits (Bitmask DP)

Se eligió Programación Dinámica con bitmask por las siguientes razones:

  • Reduce la complejidad de O(n!) (fuerza bruta) a O(n · 2n), una mejora drástica. Para n = 4: de 24 a 64 operaciones; para n = 10: de 3.628.800 a 10.240.
  • Es aplicable directamente al problema de asignación con restricción de exclusividad.
  • La máscara de bits codifica de forma compacta el subconjunto de administradores ya utilizados, permitiendo una representación de estado eficiente.
  • Permite reconstruir la solución óptima mediante un arreglo parent[] sin costo adicional significativo.

Descripción de la estrategia:

  1. Estado: dp[mask] representa el costo mínimo para asignar los administradores cuyos bits están encendidos en mask a los primeros popcount(mask) grupos.
  2. Caso base: dp[0] = 0 (ningún grupo asignado, costo cero).
  3. Transición: Para cada mask, sea k = popcount(mask). El grupo que se está asignando es grupo = k - 1. Para cada administrador j cuyo bit está encendido en mask:
    dp[mask] = min(dp[mask], dp[mask ^ (1 << j)] + costos[grupo][j])
  4. Respuesta: El mínimo entre todos los dp[mask] donde popcount(mask) = nGrupos.
  5. Reconstrucción: Se usa un arreglo parent[mask] que almacena qué administrador fue asignado en cada paso, permitiendo recorrer la solución hacia atrás.

2.3. Complejidad del algoritmo y del programa

Aspecto Complejidad Justificación
Llenado de tabla DP O(n · 2n) Se recorren 2n máscaras, y para cada máscara se evalúan hasta n administradores.
Búsqueda del óptimo O(2n) Se recorren todas las máscaras buscando la de menor costo con exactamente nGrupos bits.
Reconstrucción O(n) Se recorre el arreglo parent n veces (una por grupo).
Total temporal O(n · 2n) Dominado por la fase de llenado de la tabla DP.
Total espacial O(2n) Dos arreglos de tamaño 2n: dp[] y parent[].
Comparación con fuerza bruta: La fuerza bruta evaluaría todas las permutaciones posibles con complejidad O(n!). Para n = 20, eso serían 2.432.902.008.176.640.000 operaciones (inviable), mientras que DP bitmask requiere 20 · 220 = 20.971.520 operaciones (instantáneo). Para los tamaños típicos de la red social (n ≤ 20), la solución es prácticamente óptima.

2.4. Explicación de la implementación

La mejora se implementó en la clase AsignacionAdminDP dentro del paquete org.uade.progra3.negocio. Se crearon además dos clases de modelo: Grupo y Administrador.

Flujo de ejecución:

  1. El DataLoader lee del JSON la lista de grupos, administradores y la matriz de costos de asignación.
  2. RedSocialServicio.calcularAsignacionOptima() prepara los arreglos de nombres y delega en AsignacionAdminDP.asignar().
  3. El método asignar() ejecuta el algoritmo DP bitmask:
    • Inicializa dp[0] = 0 y todo lo demás en Integer.MAX_VALUE.
    • Para cada máscara de 1 a 2n − 1, calcula cuántos bits tiene encendidos (Integer.bitCount) para determinar qué grupo se está asignando.
    • Si el número de bits supera el número de grupos, se salta esa máscara.
    • Para cada administrador presente en la máscara, se evalúa si asignarlo mejora el costo mínimo.
  4. Busca la máscara final con exactamente nGrupos bits y menor costo.
  5. Reconstruye la asignación recorriendo parent[] de atrás hacia adelante.
  6. Retorna un ResultadoAsignacion con: costo total, arreglo de asignación, nombres y matriz de costos.

Integración con el resto del sistema:

  • demo-red-social.json fue extendido con las secciones "grupos", "administradores" y "costoAsignacion".
  • DataLoader fue modificado para parsear estas nuevas secciones opcionales.
  • RedSocialFrame agrega una pestaña “Asignación admins (DP)” que muestra la matriz de costos y el resultado óptimo.

Método principal — asignar(): Llenado de la tabla DP
Archivo: src/main/java/org/uade/progra3/negocio/AsignacionAdminDP.java

public static ResultadoAsignacion asignar(int[][] costos,
                                          String[] nombresGrupos,
                                          String[] nombresAdmins) {
    int nGrupos = costos.length;
    int nAdmins = costos[0].length;

    if (nAdmins < nGrupos) {
        throw new IllegalArgumentException(
            "No hay suficientes administradores para cubrir todos los grupos");
    }

    int totalMasks = 1 << nAdmins;

    // dp[mask] = costo mínimo para asignar los admins del mask
    //            a los primeros popcount(mask) grupos
    int[] dp = new int[totalMasks];
    int[] parent = new int[totalMasks];
    Arrays.fill(dp, Integer.MAX_VALUE);
    Arrays.fill(parent, -1);
    dp[0] = 0;  // caso base: sin grupos asignados, costo 0

    // Llenar la tabla DP
    for (int mask = 1; mask < totalMasks; mask++) {
        int k = Integer.bitCount(mask);  // admins usados = grupos asignados
        if (k > nGrupos) continue;       // no necesitamos más admins que grupos

        int grupo = k - 1;  // índice del grupo que se está asignando

        // Probar cada admin j que esté incluido en este mask
        for (int j = 0; j < nAdmins; j++) {
            if ((mask & (1 << j)) == 0) continue;  // admin j no está en mask

            int maskPrevio = mask ^ (1 << j);        // mask sin el admin j
            if (dp[maskPrevio] == Integer.MAX_VALUE) continue;

            int nuevoCosto = dp[maskPrevio] + costos[grupo][j];
            if (nuevoCosto < dp[mask]) {
                dp[mask] = nuevoCosto;
                parent[mask] = j;  // recordar la decisión
            }
        }
    }

    /* ... búsqueda del óptimo y reconstrucción ... */
}

Búsqueda del óptimo y reconstrucción de la asignación
Archivo: src/main/java/org/uade/progra3/negocio/AsignacionAdminDP.java

// Encontrar el mask óptimo final (exactamente nGrupos bits encendidos)
int mejorMask = -1;
int mejorCosto = Integer.MAX_VALUE;
for (int mask = 0; mask < totalMasks; mask++) {
    if (Integer.bitCount(mask) == nGrupos && dp[mask] < mejorCosto) {
        mejorCosto = dp[mask];
        mejorMask = mask;
    }
}

// Reconstruir la asignación mediante backtracking sobre parent[]
int[] asignacion = new int[nGrupos];
int mask = mejorMask;
for (int g = nGrupos - 1; g >= 0; g--) {
    asignacion[g] = parent[mask];
    mask = mask ^ (1 << parent[mask]);
}

return new ResultadoAsignacion(mejorCosto, asignacion,
                               nombresGrupos, nombresAdmins, costos);

public AsignacionAdminDP.ResultadoAsignacion calcularAsignacionOptima() {
    List<Grupo> grupos = dataLoader.getGrupos();
    List<Administrador> admins = dataLoader.getAdministradores();
    int[][] costos = dataLoader.getCostoAsignacion();

    if (grupos.isEmpty() || admins.isEmpty() || costos == null) {
        throw new IllegalStateException(
            "No hay datos de grupos/administradores cargados");
    }

    String[] nombresGrupos = grupos.stream()
        .map(Grupo::getNombre).toArray(String[]::new);
    String[] nombresAdmins = admins.stream()
        .map(Administrador::getNombre).toArray(String[]::new);

    return AsignacionAdminDP.asignar(costos, nombresGrupos, nombresAdmins);
}
